# G26 Pass 44 | Independently Authorized Supervised MSI Rollback Execution

**Checkpoint:** Cluster v0.546.0 G26 Pass 44. **Parent:** Pass 43. **Scope:** native Go package-stager, signed server grant, Qt trust boundary, Desktop Packages operator controls and recovery evidence. **Status:** Source implementation, **not live Windows certification**.

## Implementation

- Adds a separate, default-disabled `msi-rollback` grant-issuing route requiring administrator authorization, device entitlement and **both** `CLUSTER_ALLOW_SUPERVISED_MSI_ROLLBACK_GRANTS=true` and `CLUSTER_ALLOW_SUPERVISED_MSI_ROLLBACK_EXECUTION=true`. The short-lived, one-use signed grant binds the **original installation receipt**, **retained original MSI digest**, **completed upgrade journal**, and **upgraded MSI digest**. Neither the operation nor the four-hash grant is accepted as an install, repair, uninstall, upgrade, or content rollback grant.
- Adds `rollback-msi` as a distinct native CLI action. It re-verifies the signed *predecessor release*, its original installation receipt, Windows Installer ProductCode registration at the successor version, the exact completed upgrade journal, both retained MSI hashes, and known Package dependency blockers. It accepts **zero known dependent Packages** for execution. This is intentionally narrower than automatically modifying a transitive dependency tree.
- Creates an immutable first-write `msi-lifecycle/rollback_<packageKey>.json` prepared journal **before** consuming the one-use grant. The original `msi-attempts` installation receipt and the `msi-lifecycle/<packageKey>.json` completed upgrade journal remain unchanged. The rollback journal subsequently records launch committed / unknown outcome before resuming any Windows Installer process. Any later invocation finds this journal and refuses automatic replay, even after a process failure.
- On Windows, holds the prior and successor MSI files by their validated read-only, write/delete-denying OS handles through one suspended, Job-supervised `msiexec /i <predecessor.msi> /qn /norestart ALLUSERS=2 MSIINSTALLPERUSER=1` attempt. Checks the live ProductCode registration, journal, dependencies and source identities before resuming the suspended child. **No fallback uninstall, forced downgrade, automatic retry, or multi-Package operation** exists. The external Windows Installer service is outside the supervised process Job Object.
- Extends read-only profile inventory to include separate `msi-rollback` records alongside preserved upgrade records; the profile snapshot includes both. Native Qt and renderer independently validate a rollback record's identity, exact digest relationship to the original upgrade record and bounded OS registration observation. Desktop has a distinct typed `ROLLBACK <packageKey>` confirmation and `Inspect MSI rollback attempt journal…` control. An MSI exit code 0 or 3010 is **not** proof of installed ProductVersion, completed custom actions, correct data, or application health.

## Explicit remaining source work and certification gates

- A real Windows Installer **downgrade is not guaranteed** for an installed same-ProductCode MSI. Windows version/product semantics, custom actions, locks, reboot constraints, side-by-side dependencies and data compatibility require genuine Windows runtime testing. If the engine refuses this constrained attempt, the journal remains manual-review-required; this implementation does not attempt aggressive recovery.
- **Transitive dependents-first rollback is planned/read-only only.** Every affected Package still needs its own administrator-granted, retained-source-verified, non-replayable operation. No orchestrated cascade exists. Do not claim dependency-aware automatic rollback.
- OS ProductCode registration and installer exit observations are **not application health attestation**. A complete Windows/Qt/PostgreSQL/Garnet/10+-user acceptance run remains needed before production release. The current environment lacks a linked Qt Windows toolchain and real Windows MSI runtime; cross-compilation is not execution.
- G26-10, G26-11, CERT-12 remain **open**. Certification does not block subsequent source development.
