# Cluster v0.546.0 | TD6 G26 Workstream 4: Durable Upload Commit and Recovery

**Parent:** G26 Workstream 3 (Packet Release Acknowledgment). **G26 OPEN**; G25 SOURCE-CLOSED. This is a source implementation checkpoint, not production certification.

## Connected problems closed in this source pass

1. **Proxied resumable chunks:** `appendClusterChunk` now serializes with state changes, checks the authoritative database cursor, reconciles only trailing bytes beyond its committed offset after an interrupted write, retries legal short writes, calls FileHandle.sync before advancing the DB offset and conditionally commits the new cursor. Failure to commit restores the last committed file length. Mismatched offsets, malformed ranges and staging shortfalls fail closed.
2. **Proxied completion:** completes under the *same* local lock, reloads fresh status/offset, hashes streamed staging bytes and verifies optional checksum, renames only after full validation, commits using a conditional OPEN/offset update, restores the original partial path on DB failure, and supports idempotent completion using the actual committed digest. No dirty partial file is published as complete.
3. **Pause/resume/cancel:** status changes coordinate with the local chunk/complete lock and check expected status; cancellation never removes cluster staging while an active mutation owns that lock. For cluster mode, a DB deletion precedes filesystem disposal, leaving recoverable bytes on cleanup error. An OS filesystem lock is not an atomic cross-node DB lease; **never automatically steal one because it is older than two minutes**. Suspected orphan locks return `UPLOAD_LOCK_RECOVERY_REQUIRED` for operator reconciliation.
4. **Library and storage copies:** verified completed local uploads cannot be symlinked/hardlinked outside their staging ownership; resolved completed local sources are checked before use. `copyCompletedUploadToFile` streams local or remote source bytes, computes SHA-256, checks both exact size and checksum, syncs destination bytes and removes only a destination it exclusively created if transfer/verification fails. An existing destination is preserved on EEXIST, and same-size corruption no longer passes Library import/mounted-file staging.
5. **Direct multipart consistency:** a completed upload cannot be idempotently returned for a different asserted digest; multipart completion validates the *full contiguous sequence and expected size of each part*, not just sum and count.
6. **Client / Sync Center source:** a server error, interrupted commit or destination validation no longer implicitly DELETEs server staging. A recovered upload mismatching the selected filename/length or in a paused/recovery state requires explicit review, not silent disposal. The durable Blob queue retains local files after non-network failures and pauses 409 conflicts instead of repeatedly replaying them. Explicit user discard requires server acknowledgment before removal of its local queue entry.

## Limits and follow-ups

- **No live Node24 full tsc/build, generated Prisma client, PostgreSQL migration, real S3 multipart contention, multiuser browser/Qt/Windows/native stress/certification.** No new migration in WS4. Source test harness runs on Node22. The filesystem tests use real temp files, but database and provider services are mocks.
- `UPLOAD_LOCK_RECOVERY_REQUIRED` requires an **operator** to confirm no other process owns the session and reconcile DB cursor, staged file and job ownership before removing an orphan `.mutation-lock`. Do not delete locks based only on elapsed time or when multiple nodes may share staging. No automated stale-lock clearing is authorized by this pass.
- This is not a cross-node distributed lease. Direct multipart upload part acknowledgment, provider multipart completion and upload cleanup still need DB state fencing/real provider race tests. The browser resumed-file binding currently confirms filename/length, not an independent whole-file SHA before transfer. A malicious same-name same-size replacement remains outside this checkpoint. Storage root is trusted operator configuration; filesystem checks reduce but do not eliminate link-swap TOCTOU races without platform-specific handle-based confinement.
- Live integration must test interruption between fsync and cursor update, rename and DB commit, server restart, pause/abort races, expired-session pruner with an active writer, large-file disk budget, and repeated direct-part confirmation. Align upcoming G26 work with Library bulk retention/legal holds, Packet required recipients, Packages, Inventory/Vault, native package install recovery.
