**Parent:** G26 Workstream 5. **State:** source implementation checkpoint, G26 OPEN, G25 SOURCE-CLOSED. No production certification is implied.

## Connected implementation

1. **Required Packet release acknowledgment:** `PacketReleaseRequirement` records one immutable assignment per (release, recipient). Every assignment stores the exact publication manifest SHA-256, assigning actor, optional due date and assigned timestamp. The PostgreSQL migration `20261030000000_td6_g26_packet_required_release_delivery` adds a restrictive FK to PacketRelease and the unique recipient/release index; it has NOT been applied to live PostgreSQL.
2. **Frozen-audience / authorization:** Packet editors with source edit visibility can request a bounded candidate list (maximum 500 active accounts) and assign at most 100 recipients per request. Recipient identity and membership are rechecked against the frozen release audience using **strict** normalized People/Team/Project reads; data-source failures do not become permissive exclusion-audience matches. The server refuses stale SHA hashes, withdrawn releases, malformed IDs, ineligible/archived accounts, duplicated input, and unauthorized manager access.
3. **Transactional assignment:** `POST /api/packets/:packetId/releases/:releaseId/requirements` uses a `FOR UPDATE` lock on the release row shared with acknowledgment/revocation, performs idempotent `createMany(skipDuplicates)`, and records a canonical Activity Event inside the same serializable transaction. A write/audit failure rolls back all assignments. An existing assignment and due date are preserved on a repeat request; modifications are not silently overwritten. P2034/P2002 races produce a conflict response for reload.
4. **Scoped outcome evidence:** `GET /.../requirements` paginates release-scoped assignments and looks up exact-manifest acknowledgments, preserving history after revocation. The recipient's published-release listing projects only their own required/acknowledged state and due date. This is separate from normal Packet training completion and from delivery-issuance evidence. Neither download nor catalogue browsing is counted as acceptance.
5. **Reader and manager UI:** In the existing Packets workspace, authors can inspect a release's eligible recipients, select accounts, choose an optional due date and review pending/acknowledged assignments. Recipients see Required/Acknowledged and due date on their published release. No extra polling was added, and all recipient/report requests are on demand.
6. **Privacy:** Self-service counts and bounded exports now include subject-owned Packet requirements. Erasure planning records those requirements among pseudonymized historical evidence. Privacy export schema increments to v10. Historical assignments do not bypass erasure or authorize new access.
7. **Upload reconciliation diagnostics:** New administrator-only read-only `/api/library/transfers/recovery` returns a bounded, cursor-checked projection of FINALIZING, REVIEW_REQUIRED, ABORTING and CLEANING sessions. It shows enough provenance for investigation, but does **not** reveal object keys, multipart IDs, provider URLs, ETags, local paths, or deletion credentials. Library administrators have an on-demand UI for reviewing the queue. This deliberately does not force retry, release locks, confirm provider results or remove remote objects; no provider generation fencing exists to certify those actions.

## Limits and remaining G26

**NOT RUN:** Prisma schema generation/full type checking against generated client, PostgreSQL migration and actual `FOR UPDATE` contention, live object storage verification, browser multiuser/revocation acceptance, Node 24 application build, Windows native service or Qt client certification. Controlled route mocks validate source transition design, not deployment semantics. The Packet assignment table does not replace Studio policy sign-off or existing Packet completion. Large recipients roster is deliberately capped at 500; larger studios require server-side filtered/paginated selection. Due-date notification/escalation automation remains future work. Upload recovery only **inspects**, and remote deletion is not authorized.
