# Cluster v0.524 | Signed managed-content deployment, native rollback and honest receipts

## Implemented in this source pass

1. **Independent server deployment authority:** Dedicated Ed25519 control signer configured from a private PEM string or protected file, optional and fail-closed. New `POST /api/me/packages/:id/releases/:releaseId/authorize-content` requires a live authenticated verified Desktop device proof; it re-reads current registration, package entitlement, key, channel and rollout/pin inside a Serializable transaction. It issues a 60-second, release/digest/key/device/operation-specific grant and creates an auditable issuance event, rate-limited per Package/user. No grant when control key is unconfigured, current release is revoked, device revoked or rollout no longer authorizes it.
2. **Native trust and explicit user consent:** Qt has separate native control-key fingerprint enrollment with double entry and confirmation, distinct from the Package signing pin. The renderer never supplies a trust pin. It requests a fresh signed grant for the specific selected target, and Qt requests an explicit native confirmation and file picker for the kit. The local short-lived handoff file is removed after the helper finishes. Session changes and existing single-flight safeguards still terminate the native helper.
3. **Managed-content deployment and rollback:** Go validates two independent Ed25519 identities, the grant signature, exact requested operation/package/version/platform/digest/signing key, issue/expiry times, 24-byte nonce, the signed staging kit and every staged ZIP entry. It consumes each nonce once per private root; materializes a checksum-reverified copy under `managed/<package-key>/<sha256>`; atomically switches a dedicated managed-content pointer with monotonic generation and previous selection; rollback needs its own new grant for that exact previous release. Symlinks, malformed grant files, replay, modified staged/managed bytes and mismatched trust pins fail closed. No executable launch, system-directory installation or OS-health assertion.
4. **Nonattested reporting and UX:** Desktop Device Packages exposes provision-control-trust, authorized managed selection and rollback, success/failure status. On successfully observed managed selection with a still-live one-time staging receipt, the renderer advances the canonical deployment report from `staged` to `content_selected`, explicitly as device-reported and never as proof of OS installation. Expired/missing receipts leave local-only status rather than fabricated server success.
5. **Operational provisioning:** `tools/scripts/cluster-package-deployment-keygen.mjs` creates a distinct one-time Ed25519 control key in a non-overwriting private file, and prints only its public-key fingerprint and setup instructions. Native Go README, scope and threat boundaries updated.

## Certification boundaries

- This is a **managed-content deployment** operation, not a privileged OS software installer. No arbitrary scripts, services, DLL execution or OS installation/activation. There is no independently attested device health.
- Grants are local bearer capabilities, not machine-bound or remotely one-time-consumed. They expire after 60 seconds based on the local clock, so they do not enforce *instantaneous* revocation if policy changes during that window. Native trust files are user-profile-local, not secure hardware provisioning.
- The full Qt Windows build/run and Windows filesystem locks/ACLs were not available here. PostgreSQL transaction behavior, Node24 dependency-backed semantic compilation and Windows Qt UI remain unverified. A Go Windows x64 helper was cross-compiled, not executed on Windows.
- Source-level regression: 73/78 suites pass, five inherited WIP57 failures remain unchanged from 0.523. Focused grant assertions, Go unit/negative tests, and actual TypeScript-signer-to-Go-stager integration pass.
