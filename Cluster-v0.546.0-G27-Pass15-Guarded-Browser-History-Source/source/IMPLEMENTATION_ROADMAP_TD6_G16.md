# Cluster 0.546.0 | TD6 G16: Content-Addressed Package Artifacts and Durable Transport Foundations

**Baseline:** G15. **Status:** G16 source implemented; **NOT** full feature closeout or runtime certification. **Priority:** finish TD6 functionality, then TD7 cleanup, then full runtime acceptance. All CD-01 through CD-20 requirements remain authoritative.

## Implemented together

1. **Shared storage reuse, no duplicate storage engine.** New `managed-package-artifact-store.ts` builds Package blob authority on Cluster's existing `ClusterStorageRuntime`, which already supports secure local/shared/S3-backed storage, streaming writes and ranged reads. Package artifacts use deterministic `packages/sha256/xx/<sha256>` keys, SHA-256 verification and immutable release metadata. No new weak web-accessible blob endpoint.
2. **Actual release publication integration.** When the production server supplies `storageRuntime`, newly published signed ZIP releases write and verify the hash-addressed provider object before committing the release metadata. A storage failure refuses publication. Orphaned objects following a failed DB transaction are *not deleted* in-request because another publisher might refer to the same digest. Garbage collection is not enabled. Existing database-byte releases remain readable.
3. **One release authority.** Prisma migration adds `artifactStorageProvider`, `artifactStorageTier`, `artifactStorageKey`, makes legacy `artifact` nullable, and enforces **SQL CHECK: exactly one of SQL bytes or a complete provider locator**. The signed artifact identity and Ed25519 publisher signature remain authoritative. The server derives/validates the expected storage key from SHA-256, not from a user-supplied path.
4. **Signed device download compatibility.** Existing full download, 4 MiB first-range download, protected resume and admin release export use one verified read path for SQL or provider-backed releases. Before returning bytes, the provider-backed path verifies full object size/SHA-256 as a stream; range bytes remain bounded. Desktop device proof, per-user Package entitlement, device binding, active rollouts/pins, revocations and replay protections still apply. **Full release downloads still materialize bounded bytes in memory**, so this is not yet unbounded HTTP streaming.
5. **Reauthorization after interruption.** `POST /api/me/packages/:id/releases/:releaseId/download/recover` rotates the nonce of an *existing*, eligible, uncompleted device offer after fresh device proof, entitlement, release signature and object checks. It enforces a 24-hour offer age and at most five rotations. An expired previous nonce cannot be replayed; no additional deployment offer is issued. A native transport checkpoint may persist only deployment ID, checksum and progress, **never the bearer challenge**.
6. **Native disk checkpoint helper.** The existing Go Package stager gains `transfer-begin`, `transfer-append`, `transfer-inspect`, `transfer-commit`. It uses a private SHA-addressed root, bounded 4 MiB stdin chunks, strict sequential offsets, an exclusive operation lock, atomic checkpoint replacement, streaming file hash checks and final SHA-256-before-promotion. Inconsistent or crashed state **fails closed and requires manual reconciliation**. Completion means a verified transport file, *not* an authorized/verified Package installation. Native staging still requires the separate existing signed-ZIP, key pin and deployment/installer-grant checks.
7. **Coverage.** G16 CAS tests exercise in-memory and real `LocalStorageProvider` reads/writes/tampering and migration/route contracts; the inherited registered device-delivery route tests exercise reauthorization, permission withdrawal, rotated nonce rejection, device revocation and the recovery cap. New Go tests exercise durable transfer begin/append/inspect/commit, bad offsets, checksum failures, unsafe checkpoint symlinks, stranded locks, and size guards. Source scan + signed Package regressions retained.

## Explicit remaining limits (DO NOT label production-complete)

- **Upload capacity unchanged.** New publication still requires the legacy signed ZIP/base64 request and whole-ZIP ZIP-index validation; ordinary Packages are 4 MiB and MSI packages are 32 MiB. The server now stores new release bytes outside PostgreSQL, but does **not** yet accept multipart/streaming multi-GB uploads.
- **Desktop handoff unfinished.** The native Go disk checkpoint CLI exists and is testable, but the authenticated Qt/WebChannel package downloader has **not yet been rewired to drive it**. Renderer still assembles the current bounded ZIP in memory, and the existing Qt kit transfer remains its own short-lived flow.
- **Provider/object governance.** True immutable write-if-absent generations, provider-level fencing during concurrent writes/reads, crash-safe orphan inventory and physical garbage collection, S3/SMB fault recovery and disk-space reservation require implementation and later runtime certification. Source-level SHA checking is not a replacement for those conditions.
- **Large native ZIP validation** still reads and expands bounded ZIPs; the signed Package manifest + ZIP validator + native stager require streaming ZIP support before supporting real 2 GiB files. Native transfer size ceiling is only a staging budget, **not an installer-supported-size claim**.
- **Other TD6 feature gaps** remain open, including Calendar exceptions/delegated editing, Library video/per-recipient derivatives, wider transfers and feedback, OS repair/uninstall, cross-Package recovery, Help Center and remaining CD-01–CD-20 closeout. Preserve existing `TD6_G07_CD01_CD20_FEATURE_LEDGER.md` as ledger; do not label a CD item complete because one batch landed.
- Full Node 24 with workspace dependencies, Prisma migrations on PostgreSQL, real concurrent device requests, Windows/Qt, MSI execution, local/SMB/S3 fault recovery and release certification are deliberately deferred by user instruction. The migration requires verification before deployment.

2. Build a first-class streaming signed upload pipeline using resumable upload sessions and validation of ZIP index/entries from disk; remove the 32 MiB cap only when both the server and independent native verifier can handle larger files safely.

4. Implement other unfinished CD owner workflows in grouped batches, not indefinite MSI-only passes.
