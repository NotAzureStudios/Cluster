# Cluster v0.546.0 | TD6 G26 Workstream 3: release acknowledgment & privacy evidence

**Parent:** G26 WS2. **Status:** source implementation checkpoint, G26 OPEN. G25 SOURCE-CLOSED. **Node24 + PostgreSQL + Prisma generation + authenticated multiuser + Windows/Qt certification NOT RUN.** This is not a release-acceptance certificate.

## Why this pass

Workstream 1 preserved authorized detached derivative delivery, but its `PacketDeliveryReceipt` established only that Cluster *issued bytes*, not that a recipient reviewed or saved them. Workstream 2 established exact-version media-review decisions. Published Packets still lacked a separate, recipient-initiated and immutable-publication-bound acknowledgment. Treating download issuance, a catalogue page visit, a mutable PacketDefinition `completion`, and a recorded human decision as the same event would create incorrect audit evidence.

## Implemented together

1. **Immutable publication-bound assertions:** `PacketReleaseAcknowledgment` has a unique `(releaseId, recipientId)` pair, immutable version label, content manifest SHA-256, recipient identity and server-issued timestamp. New migration `20261029000000_td6_g26_packet_release_acknowledgment` indexes author history and recipient lookup and preserves evidence with a restrictive release FK. No source Library path or source item hash is stored.
2. **Actual authorized action:** `POST /api/packets/:packetId/deliveries/:releaseId/acknowledge` requires the authenticated Packet viewer, currently visible Packet, frozen release audience, nonrevoked verified manifest, user's explicit `confirmed: true` and exactly observed version/hash. Client cannot assert actor/time or change release content; mismatches are 409, absent authority/revoked versions are hidden. All other request fields are rejected. Duplicate confirmation is idempotent.
3. **Revocation ordering:** a serializable transaction issues `SELECT … FOR UPDATE` on `PacketRelease` before the final validation and inserted acknowledgment. The existing release-revocation update also locks that row. With an actual PostgreSQL database this prevents revocation from committing between the final check and the acknowledgment commit. Serialization/unique conflicts yield 409 requiring revalidation, not a false success. Live contention tests are still required.
4. **Separate self and author reads:** `GET /api/packets/:packetId/deliveries/:releaseId/acknowledgment` returns only the current user's acknowledgment for an authorized active release. `GET /api/packets/:packetId/releases/:releaseId/acknowledgments` requires edit authority and editable Packet visibility; it supports bounded 1–100-page cursor history, release-owned cursor checks, recipient display names, revoked-release history and no source content. Neither endpoint is a raw Library grant.
5. **Recipient and author UI:** published release inspector shows an explicit unchecked opt-in checkbox tied to the selected version and a distinct `Record my acknowledgment` button, committed timestamp, release digest and error/retry feedback. It cannot automatically infer acknowledgment from downloading a bundle, opening an inspector, or marking a mutable Packet definition complete. Admin release inspector gains on-demand historical acknowledgment evidence separate from issuance receipts. Changing selected releases invalidates stale UI requests and clears local confirmation.
6. **Self-service privacy inclusion:** export schema v9 adds bounded subject-only issued Packet downloads and recipient acknowledgment collections and a Packet evidence summary category. The erasure preview makes the retention boundary explicit: the account is pseudonymized and historical issuance/acknowledgment audit records are retained subject to legal policy. Recipient lists resolve pseudonymized users through the existing account projection. No new direct delete/cascade of committed evidence.

## Known limits and next G26 owners

- **This is human-attested acknowledgment, not proof of reading, preview opening, browser download completion, cryptographic identity signing, policy acceptance or workforce completion.** It does not satisfy legal e-signature needs. Per-release required assignments/quorum and explicit review invitations are still open; the mutable Packet completion mechanism remains distinct.
- Current route tests use a Prisma-shaped controlled driver and TS transpilation. **Generate Prisma client, apply both pending G26 migrations and test real PostgreSQL `FOR UPDATE` versus revocation, duplicate confirmations and isolation level.** Confirm transaction time, revocation contention and real authorization revocation in multiple authenticated browser clients.
- Apply retention configuration/privacy request policy for audit evidence, including review decisions, publication receipts, personnel records and resolved accounts. A pseudonymized account still has an ID linked to historical evidence. This pass documents the current preservation rather than claiming full anonymization.
